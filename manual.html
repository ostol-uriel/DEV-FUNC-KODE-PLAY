Stage 1 · Prepare

Prepare PostgreSQL and MongoDB

Before you open GRASYA, ask your database administrators to confirm a few things.

PostgreSQL (source)

  • Logical replication is supported and enabled.
  • The login can read the schema you want to migrate.
  • The replication account can create or use the publication and slot.
  • Tables have primary keys.

MongoDB (target)

  • The connection URI is reachable from the GRASYA cloud service.
  • The account can create, read, update and delete data.
  • The target database name is approved and has enough storage.
Stage 2 · Connect

Connect through the Migration Wizard

Select Connect on the toolbar. Next checks each connection before moving on.

  1. SourcePostgreSQL host, port, database, schema, login, SSL
  2. TargetMongoDB URI and target database name
  3. CaptureKeep the values your administrator provided
  4. ReviewCheck everything, then Finish

Finish saves the configuration. It does not start copying data yet.

Step 1: entering the PostgreSQL source connection
Show more: capture settings and the Review page
  • Topic Prefix, Publication Name, Slot Name: identifiers used by the managed capture service. Concurrent migrations on the same source need different slot names.
  • Included Schema: should match the source schema unless an administrator says otherwise.
  • Replication User / Password: PostgreSQL credentials allowed to use logical replication.
  • Review page: double-check the target database, schema and detected tables. Use Back to fix anything.

Stage 3 · Configure

Tables and relationships

  • GRASYA includes every table in the selected schema. Wrong tables? Go back and pick the right schema.
  • Check the ERD Diagram tab to confirm tables and foreign-key links were found.
  • Open MongoDB Relationship Mapping, choose a mapping for each relationship, then Apply.

Embedded

Child data is stored inside the parent document. Good when you always read them together.

Referenced default

Related data stays in its own collection, linked by ID. Good for data that grows or is used on its own.

Mappings can't change while a migration runs, so set them before Run.

Choosing Embedded or Referenced
Stage 3 · Configure

Calculated fields

Recompute generated or derived columns that PostgreSQL doesn't send in live changes.

  • Select Calculated Fields on the toolbar before running.
  • Detected generated columns appear with a suggested expression, already enabled.
  • Use the checkbox to include a row, + Add field for your own, and the trash icon to remove one.
  • Select Apply. Invalid expressions are highlighted so you can fix them.

Supported functions

lower upper round abs len min max concat coalesce

Plus basic arithmetic and comparisons. Calculated fields can't change while a migration is running.

Stage 4 · Run & Control

Start and monitor a migration

Check the databases, table list, relationship mappings and calculated fields, then select Run. The Monitor tab opens automatically.

  1. SnapshotExisting rows copied to staging
  2. Verification gateSchema and data checked
  3. TransformRows turned into documents
  4. CDCLive changes keep flowing (Phase2)

Keep the Logs tab open: blue = info, green = success, yellow = warning, red = error.

The Monitor view during a running migration
Stage 4 · Run & Control

Migration controls

Pause / Resume

While running

Temporarily stops processing, then continues.

Verify

During CDC

Checks schema drift and data consistency. Resumes only if clean.

Finish Migration

During CDC

Final check, then completes the migration. Use this for success.

Disconnect

While connected

Stops the run but keeps MongoDB data so you can resume later.

Cancel

While running

Stops the run and drops the whole target database. Can't be undone.

Need to stop but keep your data? Use Disconnect, not Cancel.

Why is a button disabled?

  • Run needs a finished wizard and no migration already running.
  • Pause/Resume and Cancel need a running migration.
  • Verify and Finish only work in the CDC phase.
  • Apply buttons are disabled while running or verifying.

Stage 5 · Review & Recover

ERD, logs, DLQ and history

  • ERD Diagram: view tables, columns and foreign keys. It's read-only.
  • Logs: the first place to look when something is slow or fails.
  • DLQ: events GRASYA couldn't process. Click a row for details. There's no automatic replay.
  • Migration History: past runs with Logs, Resume and Delete.
Running Finished Halted Cancelled Failed
History never stores passwords or the MongoDB URI. You'll re-enter them when resuming.
Stage 5 · Review & Recover

Resume an interrupted migration

  1. Make sure the cloud service is reachable and nothing else is connected.
  2. Open Migration History and find the Halted entry.
  3. Select Resume and review the prefilled settings.
  4. Re-enter both passwords and the MongoDB URI.
  5. Finish the wizard, check mappings and calculated fields.
  6. Select Run. GRASYA continues from where it stopped.
Show more: other statuses and missing slots
  • Only Halted runs truly resume. Other statuses start a fresh run, which may copy all rows again.
  • If the replication slot is gone, GRASYA offers Restart as fresh migration. Only use it if a new full snapshot is acceptable.

Troubleshooting

Red status bar / "No connection to server"

Check your internet or VPN, and whether a firewall or proxy blocks GRASYA. Wait for the retry countdown or select Retry. If a run was active, check History afterwards; it may be marked Halted.

PostgreSQL connection fails

Check host, port, database, schema, username, password and the SSL setting. The server must accept connections from the GRASYA cloud service. Don't keep guessing passwords; ask the administrator.

MongoDB connection fails

Check the full URI, target database name, TLS and auth options, and trusted-IP rules. Special characters in passwords may need URI encoding. Never share the full URI.

No tables are detected

Check the database and schema name (spelling and letter case), and that the account can read schema metadata.

Capture or permission error

Ask the PostgreSQL administrator to confirm logical replication, the replication login, slot and publication permissions, and that the slot name isn't in use.

DLQ entries appear

Open the DLQ tab, note the time, phase, table/topic and error, check the logs, and fix the cause with your administrator. Entries are not retried automatically.

Verify reports schema drift or mismatches

Leave the migration paused, read the per-table logs, check for schema changes and DLQ entries, and verify again once fixed. Don't Finish until verification is clean.

A toolbar button is disabled

See "Why is a button disabled?" under Migration controls, and check the Monitor logs and status bar.

Migration won't resume after a restart

Use the Halted entry in History and re-enter credentials. If the replication slot is missing, see Resume an interrupted migration.

Data safety and glossary

Before connecting

  • Dedicated MongoDB target
  • Hostnames, ports and schemas verified
  • Least-privilege accounts

Before Run

  • Table list reviewed
  • Relationships and calculated fields applied
  • Target has enough storage

Before Verify / Finish

  • DLQ and logs reviewed
  • Drift and mismatches resolved
  • Downstream users ready

Before Cancel

  • Read the dialog fully
  • Target database name checked
  • Use Disconnect if you may resume
Never put passwords, full MongoDB URIs, keys or sensitive DLQ rows in screenshots or shared documents.

CDC
Change Data Capture: streaming inserts, updates and deletes after the snapshot.
Collection
A group of MongoDB documents, similar to a table.
DLQ
Dead Letter Queue: events GRASYA couldn't process.
Embedded
Child data stored inside the parent document.
ERD
Diagram of tables, columns and relationships.
Merkle verification
Chunk-based hash comparison of source and staged data.
Publication
PostgreSQL definition of which changes are captured.
Referenced
Related documents kept in separate collections, linked by ID.
Replication slot
Keeps the change-stream position so a run can resume.
Schema
A PostgreSQL namespace containing tables.
Schema drift
A structure change in PostgreSQL during migration.
Snapshot
The initial copy of existing rows.
Staging
Internal MongoDB area used for transformation and verification.
